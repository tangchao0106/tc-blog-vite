# Prompt Engineering 基础：如何跟大模型"好好说话"

你大概率已经用过 ChatGPT、Claude 或者文心一言了。有没有过这种体验：同样一个问题，你换个说法，模型的回答质量天差地别？

比如你问"帮我写个登录页"，它给你一堆泛泛而谈的代码骨架；但你改成"用 React + TypeScript 写一个带表单校验的登录页，邮箱格式用正则校验，密码强度实时提示，深色主题"，它给的东西就直接能抄进项目。

这种"怎么问"的学问，就是 **Prompt Engineering（提示词工程）**。它不是玄学，也不是什么神秘咒语，它就是——**怎么把你的需求，讲成人话，讲清楚，讲到位**。

今天我们从前端开发者的视角，把 Prompt Engineering 的几个核心套路一次讲透。少谈参数，多谈"为什么"。

## 先建立一个直觉：大模型是个"超级认真的实习生"

打个比方。大模型就像你刚招来的一个能力超强、但完全没接触过你们项目的实习生。

- 你只说"做个登录页"，他只能凭行业常识瞎猜，做出来八成不合你意。
- 你告诉他技术栈、约束、风格、要避开的坑，他才能做出你要的东西。

**Prompt 的本质，就是给这个"实习生"写一份足够清楚的需求文档。** 你写得越清楚，他跑偏的概率越低。

很多前端同学以为"提示词工程"是算法工程师的事，其实恰恰相反——前端同学天天跟 UI、交互、边界条件打交道，最懂怎么把需求描述清楚。你在写 PRD、写组件 API 文档上练的功夫，天然能迁移到写 Prompt 上。

## 零样本（Zero-Shot）：直接说，别给例子

最基础的用法，就是直接下指令，不给任何示例。这叫**零样本**——模型没有见过你给的"样本"，直接凭预训练学到的知识干活。

比如：

> 把下面这段用户评论分成"正面 / 负面 / 中性"三类：……
>

这就是零样本。模型在预训练阶段已经见过海量分类任务的文本，所以你直接说"分类"，它知道你要什么。

**什么时候用零样本？** 任务常见、描述清晰、你不需要特定格式或特定口吻的时候。大部分日常提问，零样本就够了。

但零样本有个坑：如果任务比较"冷门"或者"有多种合理理解"，模型容易自由发挥。比如你说"把这堆数据整理一下"，它不知道你要 Excel 还是 JSON，不知道按什么维度整理。这时候就需要往下进阶。

## 少样本（Few-Shot）：给几个栗子，模型秒懂

想象你让实习生做表格，光说"做漂亮点"他不懂。但你甩给他两张之前做好的样表，说"照这个风格来"，他立刻明白了。

这就是**少样本（Few-Shot）**：在 Prompt 里塞几个"输入 → 输出"的例子，让模型照着学。

比如你想让模型把产品名转成 URL slug，但你有自己的规则（保留连字符、小写、去掉品牌前缀）：

> 输入：iPhone 15 Pro Max → 输出：iphone-15-pro-max
> 输入：MacBook Air 13 → 输出：macbook-air-13
> 输入：Sony WH-1000XM5 → 输出：sony-wh-1000xm5
> 输入：小米空气净化器4 → 输出：？

模型看到前面三个例子，会立刻悟出你的规则，第四个基本不会错。

**少样本为什么有效？** 你可以理解为：大模型在做"下一个词预测"时，例子帮它把"任务分布"锚定住了。它不再从整个语言空间里随便猜，而是沿着例子铺好的轨道走。例子就是轨道。

前端同学写单元测试时给的"输入/期望输出"对，本质上就是 Few-Shot 思维在工程里的翻版——用具体例子定义"正确"长什么样。

## 思维链（Chain of Thought）：让它"说出来"，别"憋出来"

这是前端同学最容易忽略、但收益最大的一招。

还是那个实习生比方。你让他算"购物车满 200 减 30，再叠加会员 9 折，原价 268 最终多少钱"。如果他直接喊一个数字，你不敢信；但如果他把步骤写下来：

> 1. 原价 268，满 200 减 30 → 238
> 2. 会员 9 折 → 238 × 0.9 = 214.2
> 3. 最终 214.2 元

你一眼就能看出对不对。**大模型也一样：让它把推理过程写出来，结果往往更准。**

怎么触发？很简单，在 Prompt 里加一句"请一步一步思考"，或者"先列出你的推理步骤，再给最终答案"。这就是**思维链（Chain of Thought, CoT）**。

你可以这样类比：人在做数学题时，心算容易错，列竖式就稳。思维链就是让模型"列竖式"而不是"心算"。它把每一步的中间结果都显式生成出来，这些中间 Token 又成了下一步的上下文，环环相扣，错了也容易在中间被发现。

**注意**：CoT 主要提升"推理类"任务（计算、逻辑、多步判断）的准确率，对"翻译一段话"这种不需要推理的任务没啥用，反而浪费 Token。别滥用。

## 角色扮演（Role Prompting）：给它一个"人设"

这招你可能天天在用，但没意识到它背后的原理。

> 你是一个有 10 年经验的前端架构师，擅长性能优化。请 review 这段代码并指出潜在的内存泄漏风险。

这就是**角色扮演（Role Prompting）**。你给模型一个身份，它会自动调用与该身份相关的"知识分布"和"说话方式"。

原理上，你可以理解为：不同的角色在预训练语料里对应不同的"语域"。说"你是个资深架构师"，模型就倾向于用更严谨、更专业的语气，并优先调用工程经验丰富的那部分参数；说"你是个给小学生讲编程的老师"，它就切换到通俗比喻模式。

前端同学最实用的角色设定场景：
- 让模型当"严格的 Code Reviewer"帮你挑 bug
- 让模型当"新手同事"逼它把复杂概念讲简单
- 让模型当"产品经理"从用户视角挑你方案的逻辑漏洞

一句话，**角色不是噱头，是给模型的一个"知识检索开关"**。

## 把这几招串起来：一个实战 Prompt 长啥样

真实的工程 Prompt 通常不是单用一招，而是组合。比如你要让模型从一段用户反馈里，抽取结构化的问题标签：

> 你是一个客服数据分析专家。
> 任务：把下面的用户反馈分类到给定标签之一，并给出一句话摘要。
> 可选标签：登录异常 / 支付失败 / 加载缓慢 / UI 错位 / 功能建议 / 其他
> 规则：只输出 JSON，不要解释。
>
> 示例：
> 输入："我昨晚付钱一直转圈，最后没扣款但订单没了" → {"tag":"支付失败","summary":"支付卡在加载且订单丢失"}
> 输入："{待分类文本}" → ?

你看，这一个 Prompt 同时用了：角色扮演（客服数据分析专家）、少样本（给了示例）、约束输出（只输出 JSON）、零样本兜底（其他反馈按规则分类）。这就是工程级的写法。

## 几个新手常踩的坑

- **太笼统**：「优化一下这段代码」——不如「指出这段 React 组件的 3 个性能隐患，按严重程度排序」。
- **一次塞太多事**：一个 Prompt 又让翻译、又让总结、又让写测试，模型容易顾此失彼。拆分任务，或用 Agent 串起来。
- **漏了输出格式**：要 JSON 就明说"只输出 JSON，不要 Markdown 代码块包裹"，否则它可能给你包一层 \`\`\`json。
- **迷信咒语**：网上那些"Act as…""Ignore previous instructions"的玄学前缀，大多没用。把需求说清楚，比套模板重要得多。

## 小结

Prompt Engineering 不是"调教 AI 的魔法"，而是**把模糊需求变成精确规格的能力**——这恰好是前端工程师的看家本领。记住四个核心套路：

1. **零样本**：直接说，适合常见清晰任务。
2. **少样本**：给例子，用具体样本锚定输出格式和规则。
3. **思维链**：让它"列竖式"，推理类任务更准。
4. **角色扮演**：给身份，等于按下对应知识的检索开关。

下一篇我们聊**上下文工程（Context Engineering）**——当一次对话塞不下所有信息时，怎么管理"喂给模型的东西"。那是 Prompt 的进阶版，也是做 AI 应用绕不开的硬功夫。
