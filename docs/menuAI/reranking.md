# Reranking 重排序：RAG 的"二次筛选"

## 为什么检索之后还要再排一次？

上篇文章我们聊了 Embedding 检索——把问题变成向量，去向量数据库里找"最近邻居"。这个过程很快，毫秒级就能返回结果。

但快是有代价的。**Embedding 检索本质上是在做"语义近似匹配"，它并不真正"理解"问题和文档之间的精确关系**。

打个比方：Embedding 检索就像 HR 筛简历——看关键词匹配度，快速淘汰明显不合适的。但筛出来的简历，不一定就是最适合这个岗位的人。这时候需要面试官亲自面谈，深入了解候选人和岗位的匹配程度。

**重排序（Reranking）就是 RAG 里的"面试官"**。

它的任务是对 Embedding 检索出来的 Top-K 结果做一次精细化的相关性评估，然后重新排序，确保真正相关的内容排在最前面。

## Embedding 检索的盲区

在讲重排序之前，先搞清楚 Embedding 检索有哪些"看走眼"的情况。

### 盲区一：时间/数值敏感

用户问"特斯拉 2024 年 Q3 的净利润"，Embedding 检索可能召回"特斯拉 2023 年 Q3 的净利润"，因为两者语义极其相似，只差一个年份数字。

但 Embedding 模型对具体的数值不敏感——它编码的是"特斯拉净利润"这个语义概念，而不是"2024"这个具体年份。

### 盲区二：否定词和条件关系

用户问"哪些水果不含维生素 C"，Embedding 检索可能召回"哪些水果富含维生素 C"。因为"水果"和"维生素 C"这两个核心词的语义关联太强了，Embedding 模型可能忽略"不含"这个否定词。

### 盲区三：长文档的"平均化"问题

Embedding 通常是把整段文档压缩成一个固定维度的向量。如果文档里前半段讲 A 主题，后半段讲 B 主题，向量化后可能变成一个"四不像"——和 A 也不太像，和 B 也不太像。

用户问 A 主题的问题，这段文档可能排不上号；但实际上文档前半段高度相关。

### 盲区四：查询意图的微妙差别

"怎么学 Python"和"怎么教 Python"，Embedding 向量可能非常接近（都涉及 Python 和学习），但用户意图完全不同。

这些盲区不是 Embedding 模型"不努力"，而是它的设计决定的——**Embedding 的本质是"压缩语义"，压缩就意味着信息损失**。它擅长"大致方向对不对"，不擅长"精确匹配度有多少"。

## 交叉编码器：重排序的核心武器

### 双塔模型 vs 交叉编码器

要理解重排序，先得区分两种架构：

**双塔模型（Bi-Encoder）**：这就是 Embedding 模型用的架构。它有两个独立的"塔"——一个把查询编码成向量，一个把文档编码成向量。然后两个向量做相似度计算（比如余弦相似度）。

优点是**快**——文档向量可以预先算好存进数据库，查询时只需要算查询向量，然后做向量搜索。

缺点是**粗**——查询和文档各自编码，没有交互。"特斯拉 2024"和"特斯拉 2023"的向量可能非常接近。

**交叉编码器（Cross-Encoder）**：这是重排序模型用的架构。它不分别编码查询和文档，而是把两者拼接成一句话，直接喂进模型。

比如输入变成：`[CLS] 特斯拉 2024 年 Q3 的净利润是多少 [SEP] 特斯拉 2023 年第三季度财报显示，公司净利润达到 18.9 亿美元 [SEP]`

模型会逐层计算查询和文档之间的交互注意力，最后输出一个相关性分数（比如 0~1 之间）。

优点是**准**——查询和文档在模型内部充分交互，能捕捉到细粒度的匹配关系。

缺点是**慢**——每次重排序都要做一次完整的前向传播，无法预先计算。

### 为什么交叉编码器更准？

想象你在判断"这篇文章是否回答了这个问题"。双塔模型相当于：你先读完问题，写个摘要；我再读完文章，写个摘要。然后我们比两个摘要像不像。信息压缩了两次，很多细节丢了。

交叉编码器相当于：你读一句问题，我读一句文章，我们互相讨论、对照，逐句分析"这段内容有没有回答那个问题"。

很显然，第二种方式更准，但也更花时间。

## Reranking 的工作流程

在 RAG 系统里，重排序通常这样工作：

**第一步：海选（Embedding 检索）**

用双塔模型快速召回 Top-100 个候选文档。这一步要的是"不漏"——宁可错杀一千，不能放过一个。速度优先，牺牲一点精度。

**第二步：复赛（重排序）**

用交叉编码器对这 100 个候选逐一打分，按分数重新排序。然后取 Top-5 或 Top-10 送入大模型生成答案。

这一步要的是"精准"——让最相关的结果排在最前面。精度优先，接受慢一点的速度。

你可以把整个流程想象成选秀节目：
- **海选**（Embedding）：几千人报名，导演组快速看资料筛出 100 人。
- **复赛**（Rerank）：评委面对面考核这 100 人，打分排名，选出前 10。
- **决赛**（LLM 生成）：前 10 选手上台表演，由导师（大模型）基于他们的表现给出最终评价。

## 主流 Reranking 模型

### BGE-Reranker

BGE 系列不仅有 Embedding 模型，还有专门的重排序模型（BGE-Reranker-base、BGE-Reranker-large）。

它基于 XLM-RoBERTa 架构，支持多语言。用法很简单：把查询和文档拼接后输入，模型输出一个相关性分数。

BGE-Reranker 的优势是**开源免费、支持中文、效果扎实**。在中文 RAG 场景下，它和 BGE Embedding 搭配使用是性价比很高的组合。

### Cohere Rerank

Cohere 提供的商业 Rerank API（原名 Rerank-v3），效果很强，支持多语言。它的特点是**对长文档处理得很好**，能处理 512 甚至 4096 Token 的文档。

缺点是按调用次数收费，长期用成本不低。

### Jina Reranker

Jina AI 推出的开源重排序模型，支持 8k 上下文，对长文档友好。效果接近商业 API，但可以本地部署。

### 各大厂的"隐藏技能"

很多大模型 API 其实自带重排序能力。比如调用 GPT-4 时，你可以让模型自己判断"以下哪段文档最相关"，变相实现重排序。但这种方式成本高、延迟大，一般只在没专用 Rerank 模型时应急用。

## 多路召回 + 融合：不止一种检索方式

在实际工程里，RAG 的检索环节往往不止一条路。除了向量检索，还会并行跑其他召回策略，最后把多路结果融合在一起。

### 常见的多路召回策略

**向量召回（语义匹配）**：用 Embedding 找语义相近的文档。擅长理解同义词、近义词。

**关键词召回（字面匹配）**：用 BM25、TF-IDF 等传统算法做字面匹配。擅长找包含特定术语、专有名词的文档。

**图召回（关系匹配）**：如果知识有结构化关系（比如"React 属于前端框架""前端框架包括 Vue、Angular"），可以用图数据库做关系推理召回。

**混合策略**：向量 + 关键词 + 图，三路并行召回。

### 融合策略：怎么把多路结果合成一路？

多路召回会拿到多份候选列表，每份列表的分数体系和排序逻辑都不一样。怎么融合？

**Reciprocal Rank Fusion（RRF，倒数排名融合）** 是最常用的融合算法。它的思路是：**排名比绝对分数更可靠**。

公式很简单：对每个文档，计算它在各路召回中的排名的倒数，加权求和。排名越靠前（数字越小），贡献的分数越高。

比如一个文档在向量召回中排第 3，在关键词召回中排第 5，它的 RRF 分数就是 `1/3 + 1/5 = 0.533`。

另一个文档在向量召回中排第 1，但在关键词召回中没出现（假设排第 100），它的分数是 `1/1 + 1/100 = 1.01`。

RRF 的好处是不需要统一分数尺度，也不依赖复杂的调参，实现简单效果稳定。

融合之后，通常还会再过一遍重排序模型，做最终的精排。

## 重排序的工程实践

### 候选数量怎么定？

Embedding 召回多少条给 Rerank？这是速度和精度的权衡：

- **召回 10 条**：快，但可能漏掉相关文档。
- **召回 100 条**：平衡点，大多数场景够用了。
- **召回 1000 条**：更保险，但 Rerank 成本明显上升。

一般建议先召回 50~100 条，然后 Rerank 取 Top-5 送给 LLM。如果召回质量本身很差（比如知识库很杂），可以适当扩大召回量。

### 重排序的延迟问题

交叉编码器虽然准，但延迟是硬伤。一个文档需要几十到几百毫秒，100 个文档就是几秒。

工程上常见的优化手段：

1. **缓存**：热门查询的重排序结果可以缓存一段时间。
2. **批量处理**：把多个查询-文档对拼成一批一起推理，GPU 利用率更高。
3. **蒸馏小型 Reranker**：用大型 Reranker 的输出去监督训练一个小模型，牺牲一点精度换速度。
4. **分层 Rerank**：先用轻量 Reranker 快速筛掉明显不相关的，再用重型 Reranker 精细排前几名。

### 什么时候可以不要 Rerank？

不是所有 RAG 都需要重排序。如果你的场景满足以下条件，Embedding 检索可能就够了：

- 知识库很小（几千条以内），Embedding 检索本身就很准。
- 查询很规范，没有太多歧义或数值敏感问题。
- 对延迟要求极高，不能容忍额外几百毫秒。

反过来，如果你的知识库很大、查询很开放、对答案质量要求高，那 Rerank 几乎是必选项。

## 小结

重排序是 RAG 的"精度放大器"。它的核心逻辑是：

1. **Embedding 检索负责"不漏"**——快速召回大量候选。
2. **Rerank 负责"精准"**——精细化评估候选和查询的相关性。
3. **多路召回 + 融合**可以进一步提升覆盖率，避免单一路径的盲区。

你可以把整个检索流程想象成一个漏斗：
- 漏斗最宽处是**多路召回**（可能召回几千条）
- 中间层是**Embedding 向量检索**（筛到几百条）
- 再往下是**重排序**（精排到几十条）
- 最窄处是**LLM 生成**（只用 Top-5~10 条）

每一层都在做"筛选"，但筛选的逻辑越来越精细。Embedding 看"像不像"，Rerank 看"匹不匹配"，LLM 看"能不能用来回答问题"。
