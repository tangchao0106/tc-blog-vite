## 你有没有想过，为什么你的账单总是这么高？

如果你做的是一个 AI 应用，比如一个智能客服、一个代码助手，你会发现一个奇怪的现象：每个用户问的问题都很短，但每次调用 API 的花费却不低。钱花哪儿了？很大一部分花在了"前面那一大段没变过的内容"上——你的系统提示词、你塞进去的工具定义、你给的 few-shot 示例、甚至是你每次都先喂给模型的那个长文档。

说白了就是：用户每次只问一句"帮我退款"，你却每次都把一整本《客服手册》重新读给模型听一遍。模型很听话，每次都乖乖从头算一遍。这就像是……你每发一条微信，都得先把《用户协议》全文重新背诵给对面听。

这就是 Prompt Caching（提示缓存）要解决的问题。

## 打个比方：它很像前端的"构建缓存"

如果你写过前端，一定用过 Vite 或 Webpack。第一次 `npm run build` 要等好几秒，第二次改了一行代码再 build，为什么快了？因为构建工具把没变过的模块缓存了下来，只重新编译你改的那一点。

Prompt Caching 是完全一样的思路。

大模型收到一段输入后，要先把它从文字变成一个个 token，然后做一堆矩阵运算（自注意力），这部分的中间结果叫 KV Cache。如果你的下一条请求，前面一大段和上次一模一样——比如系统提示词和工具定义都没变，只有最后用户的问题变了——那模型其实不需要把前面那段重新算一遍，直接复用上次算好的 KV Cache 就行。

就像浏览器请求同一个静态资源时，服务器说"这文件没变，直接用你本地缓存的那份"，省了重新传输的时间。

一句话总结：**Prompt Caching = 把"没变的前缀"的算力结果存起来，下次直接复用，既省时间（延迟更低）又省钱（这部分 token 计费打折）。**

## 那"命中缓存"到底是怎么判定的？

关键在一个词：**前缀匹配**。

模型判断"这次能不能用缓存"，看的是你这次请求的开头，是不是和上一次缓存下来的内容一字不差地接得上。注意是"开头"，不是"中间某段"。就像一个书架，你只能从第一本开始连续抽，不能跳过中间抽。

所以这里有个特别重要的设计原则，我称之为**"稳定放前，变化放后"**：

- 把所有不怎么变的东西——系统提示词、工具/函数定义、固定的背景知识——放在请求的最前面；
- 把每次都变的东西——用户这一句具体的问题——放在最后面。

这样，前面一大段稳定前缀就能稳定命中缓存，只有结尾那一点点需要重新算。

反过来，如果你把"用户问题"插在系统提示词中间，那每次前缀都对不上，缓存永远命中不了，等于白做。

（可以画一张图：左边是"稳定前缀区（命中缓存）" + 右边"可变后缀区（重新计算）"，一条分割线。想象水流从左边复用管道、右边新开管道。）

## 各家厂商的"脾气"不一样

虽然思路一样，但不同厂商对缓存的"规则"细节差别很大，这点你一定要心里有数：

- **缓存多长才生效**：很多家要求前缀至少达到一定长度（比如几千 token）才值得缓存，太短没必要。
- **缓存能活多久**：通常有 TTL（存活时间），比如 5 分钟。如果用户 10 分钟没说话，缓存就过期了，下次又得重新算。
- **计费怎么打折**：输入 token 一般会有折扣（有的打 1 折，有的打 5 折），但**写缓存的那一次（第一次计算）往往原价甚至略贵**。所以缓存对"同一前缀被反复使用"的场景最划算。
- **自动还是手动**：有的厂商自动缓存你重复出现的前缀，你什么都不用做；有的需要你显式标注"从哪到哪要缓存"。

（这些具体数字以各厂商文档为准，我这里只讲"为什么"和"怎么理解"。）

## 什么时候 Prompt Caching 能帮你省大钱？

给你一个画面：你的应用有 1000 个用户同时在线，每个用户每 30 秒问一个问题。你的系统提示词 + 工具定义 + 知识文档加起来有 8000 个 token，而用户每次的问题平均只有 50 个 token。

**没有缓存时**：每个请求都算满 8050 个 token 的注意力 → 1000 个用户就是 805 万 token/轮的计算量。
**有缓存时**：那 8000 个 token 几乎都命中缓存（只算一次存起来），每轮实际新增计算只有 1000 × 50 = 5 万 token。

算下来，前面的"固定成本"被摊薄到几乎为零。这就是它香的地方。

所以最适合用缓存的场景，都有个共同特征：**"一份长内容，被很多人、很多次重复使用"**。典型的就是：

- 带超长 system prompt 的对话机器人
- 把同一份文档反复塞给模型做问答的 RAG 应用
- 工具/函数定义很长的 Agent

## 几个新手常踩的坑

1. **在前面加时间戳或随机 ID**：有人喜欢在系统提示词里写"当前时间：2026-11-01 09:29"，或者给每次请求加个 `request_id`。这会让前缀每次都不一样，缓存直接失效。时间这种"必须变"的东西，请放到结尾用户消息附近，或者用厂商提供的专用字段传。
2. **以为改一个字没事**：只要前缀里有一个 token 变了（哪怕多一个空格），从那个位置往后的缓存就全断了。缓存是"从开头连续匹配"，不是"模糊匹配"。
3. **指望它解决所有成本问题**：缓存只对"重复前缀"有效。如果你的应用每次输入都完全不同（比如纯自由闲聊），那缓存帮不上忙，得从别的方面省（比如模型路由、更小的模型）。
4. **忽略 TTL**：用户沉默超过缓存存活时间，缓存就没了，第一次"唤醒"会慢且贵。长会话要做心跳保活，或者接受偶尔的重算。

## 给你一条可落地的检查清单

下次你优化 AI 应用成本时，可以按这个顺序过一遍：

- 把系统提示词、工具定义、固定知识，**全部挪到请求最前面**，且确保它们不在两次请求间变化；
- 把用户问题、动态时间、会话里会变的内容，放到最后；
- 确认你用的厂商支持 Prompt Caching，并看清楚它的长度门槛和 TTL；
- 如果你的同一前缀被高频复用（客服、RAG、Agent），缓存基本是"白捡的便宜"，一定要开；
- 用可观测性工具盯着"缓存命中率"这个指标，命中率低就说明前缀设计有问题。

## 小结

Prompt Caching 本质上不是一个多深的技术，它的思想你早就在前端工程里用过无数遍了——**缓存没变过的东西，只重算变过的东西**。区别只是上次缓存的是 JS 模块，这次缓存的是大模型的注意力计算结果。

把它用对，你的 API 账单能砍掉一大块，响应还更快。说白了，就是别让模型每次都重新背一遍《用户协议》。
