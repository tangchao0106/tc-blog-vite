# LLM 应用架构模式：RAG、Agent、Workflow 怎么选

> 选错架构，就像把跑车开进泥坑——不是车不行，是路没选对。

当你决定在项目里引入大模型时，面临的第一个技术决策通常不是"用哪个模型"，而是**"怎么把它串进现有系统"**。

目前业界主流的三种架构模式——RAG、Agent、Workflow——看起来都在做"让大模型干活"这件事，但它们的底层逻辑和适用场景完全不同。选对了事半功倍，选错了事倍功半。

这篇文章我会用尽可能生活化的方式，帮你搞清楚这三种模式各自的"脾气"，以及在不同场景下怎么选、怎么组合。

## 一、先画一个坐标系：理解三种模式的定位

在深入讲每种模式之前，我想先给你一个"坐标系"，帮你在脑中建立一个定位图。

想象横轴是**任务确定性**，从左到右代表"结果越不可预测"。纵轴是**系统自主性**，从下到上代表"系统自己做决策的能力越强"。

三种模式在这个坐标系里的位置大概是：

- **Workflow（工作流）**：左下角。任务路径是固定的，每走一步都是预先设计好的，没有自主决策的空间。
- **RAG（检索增强生成）**：中间偏左。比 Workflow 多了一个"查资料"的环节，但查什么、怎么查，基本也是固定的。
- **Agent（智能体）**：右上角。系统会根据当前情况自主决定下一步做什么，路径不固定，结果也相对不可预测。

你可以把这三者想象成三种不同的交通工具：

- **Workflow 像地铁**：路线固定，站点明确，准点发车准点到站。适合通勤这种"每天走同一条路"的场景。
- **RAG 像导航打车**：起点和终点你说了算，但中间可以实时查路况、绕开拥堵。适合"我知道要去哪，但最优路线可能每天不同"的场景。
- **Agent 像自动驾驶**：你只说"去个适合约会的地方"，它自己决定去哪、怎么走、中途要不要停下来买束花。适合"目标模糊，需要自主探索"的场景。

## 二、Workflow：一切尽在掌控

Workflow 是最简单、最可控的一种架构。它的核心思想是：**把大模型当作流程中的一个"步骤"，而不是流程的"大脑"**。

### 典型结构

一个 Workflow 通常长这样：

```
输入 → [步骤A] → [步骤B: 调用大模型] → [步骤C] → [步骤D: 调用大模型] → 输出
```

每个步骤做什么、按什么顺序做，都是代码里写死的。大模型只是其中某些步骤的"执行器"。

### 生活类比：预制菜流水线

想象一家中央厨房的预制菜工厂。流程是固定的：

1. 洗菜（固定程序）
2. 切菜（固定程序）
3. 调味（调用大模型：根据菜品类型生成配方）
4. 烹饪（固定程序）
5. 质检（调用大模型：检查成品描述是否符合标准）
6. 包装（固定程序）

步骤 3 和 5 用到了 AI，但整个流程的结构是完全预设的。AI 只是替换掉了原来需要人工判断的环节。

### 什么时候用 Workflow？

- **流程高度标准化**：比如发票识别 → 信息提取 → 格式校验 → 录入系统。每一步该做什么非常明确。
- **需要严格审计**：金融、医疗等强监管行业，必须能追溯到每一步做了什么决策。Workflow 的每一步都是确定的，容易审计。
- **延迟敏感**：Workflow 没有"思考"的时间开销，执行路径最短，延迟最低。
- **成本敏感**：只在大模型真正必要的环节调用 API，其他地方用传统代码，成本最低。

### 局限

Workflow 的问题是**不够灵活**。如果输入稍微偏离预期，整个流程可能就崩了。比如发票识别流程，如果来了一张手写的收据而不是标准发票，Workflow 可能直接报错，因为它没有"自主调整"的能力。

## 三、RAG：让大模型"有书可查"

RAG 是目前企业级 LLM 应用中最流行的架构。它的核心思想是：**大模型本身不存储你的私有知识，而是在回答之前先去你的知识库里"查资料"，然后把查到的资料作为上下文一起送给大模型生成回答。**

### 典型结构

```
用户提问 → 向量检索（从知识库找相关资料）→ 拼接 Prompt（问题 + 资料）→ 大模型生成回答
```

你可以把 RAG 想象成开卷考试：学生（大模型）可以带一本教科书（知识库）进考场，遇到不会的题就翻书找答案，然后结合自己的理解写出回答。

### 生活类比：律师查案例

一个律师接了一个案子。他不会凭记忆直接写辩护词，而是会：

1. 去案例库里检索类似判例
2. 把相关法条和判例整理出来
3. 结合当事人的具体情况，写出辩护策略

RAG 做的本质上就是这件事。检索系统相当于律所的档案室，大模型相当于律师的头脑。

### RAG 的核心环节

一个完整的 RAG 系统通常包含几个关键环节：

**文档预处理**：把原始文档（PDF、Word、网页）切分成合适大小的片段，生成向量嵌入，存入向量数据库。

**检索（Retrieval）**：用户提问时，把问题也转成向量，去向量数据库里找最相似的文档片段。

**重排序（Reranking）**：检索可能返回几十个片段，用更精确的模型给它们打分排序，选出最相关的几个。

**生成（Generation）**：把选出的片段和用户问题一起塞进 Prompt，让大模型基于这些资料生成回答。

### 什么时候用 RAG？

- **知识频繁更新**：比如客服知识库、产品文档，今天更新的内容明天就要能回答。RAG 只需要更新知识库，不需要重新训练模型。
- **需要引用溯源**：回答里要标注"根据某某文档第 X 页"。RAG 天然支持这个，因为你知道每段资料来自哪。
- **数据隐私要求高**：敏感数据不需要送到第三方模型厂商，只需要把检索到的片段（已经脱敏或授权后）传过去。
- **幻觉控制**：有了资料作为"锚点"，大模型胡说八道的概率大大降低。

### 局限

RAG 最大的瓶颈是**检索质量**。如果检索环节没找到正确的资料，后面生成环节再强也没用。就像律师去档案室没找到关键判例，辩护词写得再好也赢不了官司。

另一个问题是**复杂推理**。RAG 适合"查到了就能答"的问题，但如果问题需要多步推理、跨文档关联分析，RAG 就可能力不从心。比如"对比 A 产品和 B 产品在三个场景下的优劣"——这需要同时查多个文档，还要做综合分析，简单的 RAG 架构搞不定。

## 四、Agent：让系统自己"想办法"

Agent 是最灵活、也最不可预测的一种架构。它的核心思想是：**不给系统预设流程，而是给它一套"工具"和"目标"，让它自己决定怎么一步一步达成目标。**

### 典型结构

```
用户目标 → Agent（思考：我要做什么？）→ 调用工具/查询资料 → Agent（思考：现在情况如何？下一步做什么？）→ ... → 完成任务
```

关键点是中间有**一个循环**：Agent 每执行一步，都会重新评估当前状态，然后决定下一步行动。这个循环可能迭代很多次，直到任务完成或者达到某个终止条件。

### 生活类比：私人管家

你对一个管家说："帮我策划一场周末的朋友聚会。"

管家不会问你"请提供详细的需求文档"，而是自己会去：

1. 查一下你的日历，看看周末有没有空
2. 问问你大概想请几个人
3. 根据人数和预算，查附近合适的餐厅或场地
4. 拟定几个方案给你选
5. 你选定后，他去预订、发邀请、安排交通

如果某个餐厅没位置了，他自己会换一家。如果你临时说"再加两个人"，他会重新调整安排。整个过程中，他自主决策、自主调整，只在需要你做决定的时候找你确认。

这就是 Agent 的工作方式。

### Agent 的核心能力

Agent 之所以"智能"，是因为它通常具备以下几种能力：

**工具使用（Tool Use）**：能调用外部 API、查数据库、读写文件、发送邮件等。工具就是 Agent 的"手脚"。

**规划（Planning）**：能把一个大目标拆成多个小步骤，按优先级排序执行。

**记忆（Memory）**：能记住之前的对话和中间结果，避免重复劳动。

**反思（Reflection）**：执行过程中如果出错了，能自我纠正。比如代码写错了，能自己看报错信息然后修改。

### 什么时候用 Agent？

- **目标明确但路径不确定**：比如"帮我写一个能爬取某网站数据的 Python 脚本"。代码怎么写没人能预先设计好，需要 Agent 自己探索。
- **需要多步推理和工具组合**：比如"分析这家公司过去三年的财报，找出异常趋势，然后查一下同期有没有重大新闻事件，最后写一份分析报告"。
- **环境动态变化**：任务执行过程中外部条件可能变，Agent 能实时调整策略。
- **需要人在回路**：复杂任务中，Agent 可以在关键节点停下来问人的意见，而不是自己闷头干到底。

### 局限

Agent 最大的问题是**不可控**。因为它自己决定每一步做什么，你可能完全不知道它下一秒会调用什么 API、花掉多少 Token、执行多久。对于生产环境来说，这是个很大的风险。

另一个问题是**成本高**。Agent 通常需要多次调用大模型（每轮循环都要推理一次），Token 消耗可能是 RAG 的数倍甚至数十倍。

## 五、三种模式怎么选？一张决策表

讲了这么多，总结一下怎么选：

| 维度 | Workflow | RAG | Agent |
|------|----------|-----|-------|
| 任务确定性 | 高（流程固定） | 中（检索不确定） | 低（路径自主探索） |
| 系统自主性 | 低（按脚本执行） | 中（检索+生成） | 高（自主规划决策） |
| 延迟 | 低 | 中 | 高 |
| 成本 | 低 | 中 | 高 |
| 可解释性 | 高 | 中 | 低 |
| 适用场景 | 标准化流程 | 知识问答 | 复杂任务 |

更实际的决策思路：

1. **先试试 Workflow**：如果你的任务有明确的步骤，先用 Workflow 把大模型嵌入到具体步骤里。这是成本最低、最可控的方案。

2. **知识密集就上 RAG**：如果回答质量严重依赖外部知识，而且知识经常更新，上 RAG。

3. **复杂任务再考虑 Agent**：如果 Workflow + RAG 都搞不定，任务确实需要自主探索和工具组合，再上 Agent。

## 六、进阶：混合架构才是常态

现实中最常见的不是"三选一"，而是**混合使用**。

### Workflow + RAG

一个标准的客服系统可能是这样：

- 用户提问 → Workflow 步骤 1：意图识别（规则 + 小模型）
- 如果是常见问题 → Workflow 步骤 2：RAG 检索知识库 → 生成回答
- 如果是投诉类 → Workflow 步骤 3：转人工

这里 Workflow 负责流程控制，RAG 负责内容生成。

### RAG + Agent

一个深度研报生成系统：

- Agent 负责整体规划：先查什么、后查什么、怎么组织报告结构
- 每个"查资料"的环节内部用 RAG：从向量数据库检索相关文档
- Agent 拿到资料后做综合分析，决定下一步还要补充查什么

这里 Agent 负责"导演"，RAG 负责"道具供应"。

### Workflow + RAG + Agent

一个复杂的合同审查系统：

- Workflow 阶段：按固定流程提取合同的关键字段（金额、期限、违约责任等）
- RAG 阶段：检索公司内部的历史合同和风险案例库
- Agent 阶段：综合分析当前合同的风险点，生成审查意见，如果有不确定的地方自动发起审批流程

## 七、写在最后

选架构就像选交通工具：没有最好的，只有最适合的。

- 通勤上班，地铁最合适（Workflow）
- 周末出游，打车最灵活（RAG）
- 探险穿越，自驾才能到（Agent）

很多团队犯的错误是"为了用 Agent 而用 Agent"——明明一个 Workflow 就能搞定的事，非要上多智能体系统，结果成本翻了几倍，稳定性还下降了。

我的建议是：**从简单开始，按需升级。**

先用 Workflow 验证核心逻辑，如果确实遇到知识更新的问题就上 RAG，如果确实需要自主探索再上 Agent。每一步都有明确的问题驱动，而不是技术驱动。

毕竟，架构是为人服务的，不是人为架构服务的。
