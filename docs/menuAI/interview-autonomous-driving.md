## 13. TOPS 是什么单位？需要注意哪些坑（理论算力 / 实际算力、精度 INT8 / FP16）？

TOPS = **Tera Operations Per Second**，每秒万亿次运算。它是衡量 AI 芯片算力的常用单位，比如某智驾芯片标称「254 TOPS」。

但看 TOPS 最容易踩坑，至少有四个：

1. **理论峰值 vs 实际利用率**：标称的 254 TOPS 是「理想满血」数字。真实场景里，数据搬运、内存等待、kernel 启动都有开销，实际能跑到的往往只有**三到五成**。就像一辆车标最高时速 300，你市区里实际永远到不了。所以别被纸面数字忽悠，**看实测吞吐**才靠谱。

2. **精度陷阱（INT8 / FP16 / FP32）**：TOPS 必须看「在什么精度下」。INT8（8 位整数）算力数字通常比 FP16（半精度浮点）高好几倍，比 FP32 高更多——因为低精度每次运算更省晶体管。但问题是：低精度算力强，精度（数值准确度）却差。芯片厂商常拿 INT8 TOPS 当门面，可你的模型若用 FP16 跑，实际能用的算力要打折。**一定要问清「这个 TOPS 对应哪种数据类型」**。

3. **稀疏 vs 稠密（Sparsity）**：有些标称 TOPS 是开了「结构化稀疏」的——假设权重里一半是 0 不算运算。可真实模型不总能压出这么多 0，稠密推理时数字又得砍半。要看「稠密算力」才有参考意义。

4. **内存带宽才是真瓶颈**：这是最容易被忽视的。算力再高，如果数据喂不进计算单元（带宽不够），芯片就「饿着肚子干等」。很多加速卡纸面 TOPS 很猛，实际卡在带宽上，利用率惨淡。类比：发动机马力再大，油管太细也白搭。

一句话：**TOPS 是入门参考，不是性能保证。看实际利用率、看精度口径、看带宽，三件套齐了才算数。**

## 14. 什么叫端到端自动驾驶？和传统感知‑规划‑决策拆分模式区别？

传统自动驾驶是一条**流水线**，分成几段独立模块：

- **感知（Perception）**：用摄像头 / 激光雷达识别周围——哪是车、哪是人、哪是车道线。
- **预测（Prediction）**：预测这些物体接下来怎么动。
- **规划（Planning）**：基于感知结果规划一条路径。
- **控制（Control）**：把路径变成方向盘转角、油门、刹车。

每段各有各的模型 / 规则，段与段之间用「结构化数据」（边界框、轨迹点）传递信息。问题在哪？**每段独立优化，误差会逐级累积**；而且模块之间为了通信，必须把丰富信息压缩成几个框和标签，**大量细节在接口处丢掉了**——比如「那个行人手抬起来像要过马路」这种微妙信号，常被压成一个普通边界框。

**端到端自动驾驶（End-to-End）** 则是：把原始传感器数据（图像、点云）直接灌进一个巨大的神经网络，**输出端直接是方向盘 / 油门 / 刹车指令**。中间没有人为切分的模块，模型自己学「从画面到操作」的映射。

对比画成两张图：

- 传统 = **工厂流水线**：原料（传感器）→ 分段加工（感知/预测/规划/控制）→ 成品（操作）。每段师傅各管一摊，衔接处要交接单据，单据丢信息。
- 端到端 = **老师傅凭手感一气呵成**：看见路，手直接搭方向盘。快、信息不丢、上限高。

但端到端也有硬伤：

- **可解释性差**：模型为什么这时刻打了方向盘？说不清。出了事故难定责、难调试。
- **数据饥渴**：要学出好策略，得喂海量真实 + 仿真数据，覆盖各种极端场景。
- **安全验证难**：传统模块好做单元测试，端到端整体黑箱，验证靠大规模路测和仿真。

所以业界现状是「混合路线」居多：感知端到端化（比如用 BEV + Transformer 统一感知），决策规划仍保留可解释的规则兜底。纯端到端还在攻坚，但方向很明确。
