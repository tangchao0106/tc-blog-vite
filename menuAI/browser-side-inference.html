浏览器端推理：把大模型装进浏览器里跑 ​

你有没有想过一个问题：能不能让大模型直接在浏览器里跑，不经过任何后端服务器？

放在两年前，这个问题听起来像个笑话。一个 7B 参数的模型要吃掉好几 GB 显存，浏览器连显存长什么样都不知道。但现在，这件事已经可以做到了——而且体验比你想象的好得多。

这篇文章就来聊聊浏览器端推理这件事：它怎么做到的、有哪些工具、适合什么场景，以及它跟"云端推理"到底差在哪里。

为什么要在浏览器里跑模型？ ​

先说动机。如果你只是做一个聊天机器人，调 OpenAI 的 API 就够了，为什么要折腾浏览器端？

说白了就是三个痛点：

隐私。数据不出浏览器，用户说的话、传的文件全程留在本地。这在医疗、法律、金融等场景里是刚需——你总不能把病人的病历传给第三方 API。

延迟。没有网络往返，文本生成几乎是瞬时的。云端 API 再快，也有几十到几百毫秒的延迟，用户能感觉到"卡了一下"。

成本。云端推理按 Token 收费，用户越多账单越厚。浏览器端推理的边际成本是零——用户的 GPU 是免费的。

当然也有代价：模型能力会打折。浏览器里跑不了 GPT-4 级别的模型，只能跑"瘦身版"。但很多场景不需要 GPT-4——一个 3B 的模型做文本摘要、代码补全、翻译，完全够用。

两个关键"桥梁"：WebGPU 和 WASM ​

浏览器本身没有 GPU 编程能力。在浏览器里跑模型，需要两个"桥梁"：

WebGPU 是浏览器和 GPU 之间的新通道。你可以把它理解为浏览器界的"显卡驱动接口"——它让 JavaScript 能直接调用 GPU 做并行计算。大模型的核心运算是矩阵乘法，而 GPU 天生就是干这个的。WebGPU 一出来，浏览器端推理的推理速度直接翻了 5 到 10 倍。

WASM（WebAssembly） 则是把 C/C++ 代码编译成浏览器能跑的低级字节码。很多模型的底层依赖是用 C++ 写的（比如矩阵运算库），有了 WASM，这些代码不用重写成 JavaScript，直接编译就能在浏览器里跑。

打个比方：WASM 相当于给你的 JavaScript 装了一个"涡轮增压器"，让它能跑跟原生代码差不多快的 C++ 库；WebGPU 则相当于给你接上了一块"外置显卡"，让浏览器可以真正利用 GPU 的并行算力。

目前的浏览器端推理，基本就是这两种技术的组合。只靠 WASM 跑 CPU 推理也行，但慢；加上 WebGPU 才算是真正的"可用"状态。

两大主角：WebLLM 和 transformers.js ​

现在浏览器端推理有两大开源方案，你可以理解为两个不同的"流派"。

WebLLM：专为浏览器优化的"轻量引擎" ​

WebLLM 是 MLC（机器学习编译）团队的作品。它的核心思路是：把模型提前编译成一种叫 MLC 格式 的中间表示，然后在浏览器里用 WebGPU 高效执行。

它的体验做得非常流畅。用户打开网页，模型会自动下载到浏览器缓存（通常是 IndexedDB），下载一次之后就不用再下了。模型大小通常在 1-4GB 之间——听着不小，但跟下载一部电影差不多，而且只需要下这一次。

WebLLM 支持的模型列表也很丰富：Llama、Phi、Gemma、Qwen 等主流开源小模型基本都覆盖了。你甚至可以直接在浏览器里跑一个能聊天的助手，效果跟 ChatGPT 的"免费版"有得一拼。

它的一个巧妙设计是 模型分片缓存。模型文件被切成小块，下载时像 P2P 一样并行拉取，断网了还能续传。这在前端视角来看，就跟"大文件分片上传"的思路一模一样——只不过方向反了，是下载。

transformers.js：把 HuggingFace 生态搬到浏览器 ​

transformers.js 的定位不一样。它不是从零设计的引擎，而是 把 HuggingFace 的 transformers Python 库完整迁移到了 JavaScript。

HuggingFace 是机器学习界的"GitHub"，上面有几十万个预训练模型。transformers.js 让你在浏览器里直接加载这些模型——代码接口几乎跟 Python 版一模一样。如果你用过 HuggingFace 的 Python API，切到 JavaScript 几乎是零成本。

它的杀手锏是 兼容性。HuggingFace 上的模型海量，虽然不一定每个都能跑（大小限制），但主流的小模型基本都能用。从文本分类、命名实体识别、文本生成到翻译，一条 pipeline() 就够了。

不过 transformers.js 目前也依赖 WASM 和 WebGPU 做底层计算。它的定位更像是一个"翻译层"——把 HuggingFace 的生态翻译成浏览器能理解的版本，而不是从头造轮子。

一句话概括 ​

  • WebLLM：轻量、专精、体验好，适合想"开箱即用"在浏览器里跑聊天模型的场景。
  • transformers.js：生态广、接口熟、灵活度高，适合想在浏览器里尝试各种小模型、做实验的场景。

打个比方：WebLLM 像"买一辆整车"，坐上去就能开；transformers.js 像"给你一堆零件和说明书"，你可以自己组装。

实际限制：浏览器能跑多大的模型？ ​

这个问题是所有人最关心的。答案是：看你的硬件。

纯 CPU（WASM）：最多跑 1-3B 参数的模型，推理速度在每秒几个到十几个 Token 之间。基本上就是"能用但不太爽"的水平。

WebGPU：可以跑到 7-8B 参数（量化后约 4-5GB），推理速度 20-50 Token/秒——这跟日常聊天体验已经差不多了。

实际体感：M3 MacBook 上，WebLLM 跑 Phi-3 (3.8B) 能达到 40-50 Token/秒的速度，比普通人阅读速度还快。跑 Llama-3-8B（量化版）大约 15-25 Token/秒，虽然慢一点但对话完全够用。

这里有两点需要理解：

第一，量化是"压缩"不是"阉割"。原始模型用 FP16 存参数，量化成 INT4 能压缩到原来的四分之一，精度损失通常不到 5%。你可以理解为图片的"有损压缩"——肉眼几乎看不出区别，文件大小却小了 4 倍。

第二，"参数多"不等于"用得好"。在浏览器场景下，模型大小和推理速度的权衡比绝对能力更重要。一个 3B 的模型如果响应足够快，用户体验可能比一个慢吞吞的 8B 模型更好。

前端开发者需要知道什么？ ​

如果你是一个前端开发者，想尝试在浏览器里跑模型，记住这几个关键点：

模型下载是"用户体验"不是"技术细节"。用户第一次打开页面要等 2-5 分钟下载模型，你必须在 UI 上给反馈——进度条、预估时间、后台下载。否则用户以为你的网站崩了。

Web Worker 是标配。模型推理必须放在 Worker 里跑，否则会阻塞主线程，整个页面卡死。好消息是 WebLLM 和 transformers.js 都内置了这个处理。

缓存策略是核心。模型文件应该存在 IndexedDB 里，下次打开直接用。你需要处理版本更新（模型升级了缓存失效）、存储空间不足（浏览器存储有限）等边界情况。

不要把它当主力方案。浏览器端推理更适合"辅助"和"增强"——离线场景、隐私敏感场景、低成本原型验证。如果你的产品依赖的是最先进的模型能力，还是老老实实调 API。

总结 ​

浏览器端推理已经从"玩具"进化到了"可用工具"。对于前端开发者来说，这是一个很值得关注的方向——它让你能用熟悉的 JavaScript 技术栈，做出一些以前只有后端才能做的事。

你可以从 WebLLM 开始：10 行代码，一个聊天框，就能在自己浏览器里跑出一个"离线版 ChatGPT"。这件事本身就很有意思，不是吗？
