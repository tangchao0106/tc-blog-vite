流式输出：如何在前端"接住"大模型的回答 ​

用过 ChatGPT 的人都知道那种体验：你问完问题，屏幕上的字不是"哗"一下全出来，而是像有人在对面打字一样，一个字一个字往外蹦。

这就是流式输出（Streaming）。它看起来是个 UI 小花活，但背后涉及的技术选择和工程细节，直接关系到用户体验和产品成本。

今天我们从零开始，把流式输出的来龙去脉、技术方案、前端实现，一次讲清楚。

为什么要流式？等全部生成完再显示不行吗？ ​

先说一个反直觉的事实：大模型生成回答的过程，本身就是"一个字一个字蹦"的。

模型不是先把整段话想好再一次性吐给你。它是自回归的——生成第一个字，把这个字当作上下文，再生成第二个字，再把第二个字加进上下文，生成第三个……像搭积木，搭一块看一块，直到觉得"说完了"为止。

如果你等它全部生成完再一次性展示，用户可能要盯着空白屏幕等 5 秒、10 秒，甚至更久。这种"死等"的体验，跟当年拨号上网加载图片的感觉一样让人焦虑。

流式输出的本质，就是把模型内部的"逐字生成"过程，透明地展示给用户。 用户看到字在跳，就知道"它在干活"，等待感被大大缓解了。

打个比方。你去餐厅点菜，厨师做饭需要 10 分钟。方案 A：你干等 10 分钟，菜一次性端上来。方案 B：厨师每做好一道先端一道，你边吃边等。流式输出就是方案 B——用户不用干等整桌菜，先上的先吃。

还有一个隐藏好处：首字延迟（Time to First Token） 是衡量模型响应速度的核心指标。流式输出让用户在第一个字出来时就"感知到响应"，而不是等最后一个字才"正式收到回答"。对用户体验来说，前者好得多。

核心技术：SSE（Server-Sent Events） ​

流式输出最常用的传输协议是 SSE（Server-Sent Events）。你可以把它理解为 HTTP 的"升级版"——普通的 HTTP 请求是"一问一答"，问完答完连接就断了；SSE 是"一问，答答答答……"，服务器可以源源不断地往客户端推数据，直到说完为止。

你可以把 SSE 想象成单向的水管。客户端（前端）打开水龙头，服务器（大模型 API）那边有水（生成的字）就源源不断地流过来。水流完了，水管自然关闭。

SSE 为什么适合大模型流式输出？

第一，基于 HTTP，兼容性好。 不需要 WebSocket 那么重的握手过程，普通的 HTTP 连接就能搞定。前端用 EventSource 几行代码就能接。

第二，天然的分块语义。 SSE 的每个数据块以 data: 开头，你可以把模型生成的每一个 Token 包成一个 SSE 数据块推过来。前端收到一块，渲染一块，逻辑非常干净。

第三，自动重连。 SSE 内置断线重连机制。如果网络抖了一下，前端会自动尝试重新建立连接，不需要你写额外的重连逻辑。

当然 SSE 也有局限：它是单向的——只能从服务器往客户端推，客户端不能通过同一条连接往回发消息。如果前端需要"边生成边打断"（比如用户点了"停止生成"），通常需要另开一条 HTTP 请求去发指令，或者升级到 WebSocket。

WebSocket：双向对话的"专线电话" ​

如果你需要更灵活的交互——比如用户可以随时打断、可以边生成边上传新上下文、可以多轮对话保持同一个连接——那 WebSocket 是更好的选择。

WebSocket 跟 SSE 的区别，就像对讲机和单向广播的区别。SSE 是广播电台，你只能听；WebSocket 是对讲机，双方都能说。

在 AI 应用里，WebSocket 的典型使用场景是：

  • 实时语音对话：用户说话 → 服务器识别 → 模型生成 → 语音合成 → 播给用户。整个过程要在一个连接里双向跑。
  • 协作式 AI 编程：多个用户同时跟一个 AI 助手对话，WebSocket 负责实时同步所有人的输入和模型的输出。
  • 需要打断/重试的复杂交互：用户说"前面那句不对，重新来"，前端直接通过同一条连接发指令，不需要另开 HTTP。

但 WebSocket 的代价是更复杂的连接管理。你需要处理握手、心跳、断线检测、重连策略……对于普通的"一问一答"式流式输出，SSE 通常是更轻量的选择。

前端怎么"接"流式数据？ ​

不管底层是 SSE 还是 WebSocket，前端拿到流式数据后，核心任务就一个：把源源不断的小碎块，拼成流畅的阅读体验。

这里有几个关键点：

1. 分块渲染 ≠ 逐字 append ​

最 naive 的做法是每收到一个 Token，就往 DOM 里 append 一个字符。但这会导致页面频繁重排，字一多就卡。

更好的做法是：用一个缓冲区积累一定量（比如 3~5 个 Token 或 20ms）再统一刷新 DOM。用户感知上仍然是"连续输出"，但浏览器的渲染压力小得多。你可以理解为：模型那边是"逐字生成"，但你前端展示时可以"小批量刷新"。

打个比方。模型像一台高速打印机，每秒出 50 个字。你不会每出一个字就贴到墙上，而是等它出一小叠，再一起贴。用户看墙上的字仍然是连续出现的，但你的动作次数少了很多。

2. 打字机效果的微妙之处 ​

很多产品会给流式输出加上"打字机效果"——每个字出现时有个淡入动画，或者模拟键盘敲击的声音。这看起来很酷，但要注意：动画不能拖慢实际输出速度。

如果模型每秒生成 30 个 Token，你的动画每个字花 50ms，那 30 个字就要 1.5 秒才能播完动画，用户会感觉"模型变慢了"。好的做法是动画时长跟实际数据到达速度解耦：数据来了就立刻显示，动画只是视觉点缀，不能成为瓶颈。

3. Markdown 实时解析的坑 ​

大模型输出的内容经常带 Markdown 格式（标题、代码块、列表……）。如果你在流式渲染时实时解析 Markdown，会碰到一个尴尬的问题：在接收过程中，Markdown 语法可能是不完整的。

比如模型正在输出一个代码块：

……先输出了 "```js\nconst a = "，你解析成代码块渲染了；下一秒它又输出了 "1;\n```"，语法才完整。中间那段不完整的解析结果，用户会看到奇奇怪怪的排版。

解决方案有两种：

  • 延迟解析：等收到一个完整的段落（或遇到换行），再统一解析这一段。牺牲一点实时性，换来排版正确。
  • 增量 Markdown 解析器：用支持增量解析的库（如 marked 的流式模式），它能处理"还没收完"的 Markdown，尽量保证中间状态也不难看。

4. 滚动跟随与打断 ​

流式输出时，页面通常会自动滚动到底部，让用户始终看到最新内容。但要注意：如果用户手动往上滚去查看前面的内容，自动滚动应该暂停，否则用户在阅读时会被"拽"回底部。

打断功能也很重要。用户点"停止生成"时，前端需要：

  • 立即关闭 SSE/WebSocket 连接；
  • 把已收到的内容保留在页面上；
  • 显示一个"生成已停止"的轻提示；
  • 让用户可以基于当前内容继续追问。

一个前端实现的"骨架"思路 ​

你可以把整个流式输出流程想象成一条流水线：

用户提问 → API 请求（开启 stream=true）→ SSE 连接建立
→ 服务器逐块推送 Token → 前端缓冲区累积 → 定时刷新 DOM
→ Markdown 解析 → 打字机动画 → 自动滚动/打断检测

每一步都可以根据产品需求调整粒度。比如有些产品不要求 Markdown 解析，那就跳过；有些产品对流式延迟极度敏感，那就把缓冲区设得更小。

小结 ​

流式输出不是"炫技"，而是大模型产品用户体验的基线要求。用户已经习惯了 ChatGPT 那种"边说边出"的感觉，你的产品如果等半天才一次性蹦出答案，会显得很"落后"。

记住几个要点：

  1. SSE 是默认选择：单向、轻量、基于 HTTP，适合大多数"问答式"流式场景。
  2. WebSocket 是进阶选择：双向、实时性强，适合语音、协作、复杂交互场景。
  3. 前端接数据要缓冲：不要逐字操作 DOM，小批量刷新性能更好。
  4. Markdown 解析要耐心：不完整的语法别急着渲染，等一等或上增量解析器。
  5. 打断和滚动要体贴：用户有控制权，别强迫他们被你拽着走。
