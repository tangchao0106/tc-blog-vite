结构化输出：让大模型吐出"格式化数据" ​

上一篇我们聊了上下文工程——怎么在有限的窗口里摆好信息。信息摆好了，模型也看完了，接下来一个更实际的问题来了：它吐出来的东西，你怎么用？

如果你让模型"分析一下这段用户反馈"，它可能给你回一大段散文，甚至夹几句感想。你前端要的是 JSON，它给你的是小作文。你让模型"提取三个关键词"，它可能给你编号列表，可能给你逗号分隔的字符串，也可能给你一段"好的，以下是三个关键词……"的废话。

这就是结构化输出要解决的问题：让模型按你规定的格式输出数据，不多不少，不跑题，不带废话。

一个真实的前端痛点 ​

想象你在做一个"AI 智能表单填充"功能。用户上传一张发票照片，模型识别后，你需要拿到：

{ 发票号码、开票日期、金额、税率、销售方名称 }

但模型可能给你回：

根据您提供的发票图片，我识别出以下信息：发票号码是 12345678，开票日期为 2024 年 3 月 15 日，金额……

你前端怎么解析？写正则？拆字符串？祈祷它每次格式都一样？

结构化输出的本质，就是把"自由作文"变成"填空题"。 你画好表格的格子，模型往里面填内容。前端拿到直接 JSON.parse，完事。

方法一：JSON Mode —— 最简单的"格式锁" ​

OpenAI、Claude、通义千问等主流模型都支持一个叫 JSON Mode 的功能。开启之后，模型保证输出的内容一定是合法的 JSON，不会有多余的废话，不会有 Markdown 代码块包裹。

你可以把它理解为：你给模型下了一道"格式化禁令"——"只许写字典，不许写散文"。

打个比方。模型原本是个话痨诗人，你让它描述一幅画，它能写八百字散文。JSON Mode 就像你给诗人发了一个填空表格："请填写：颜色____、主题____、情绪____"——他只能填表格，不能写诗。

JSON Mode 的用法很简单：在 API 请求里加一个参数 response_format: { type: "json_object" }，同时在 Prompt 里告诉模型你要的 JSON 结构长什么样。

但要注意一个坑：你必须在 Prompt 里明确描述 JSON 的 schema（字段名、类型、含义），否则模型不知道表格有几格、每格填什么，它可能会乱编字段名。JSON Mode 只保证"输出是 JSON"，不保证"JSON 长啥样"。

方法二：Function Calling —— 让模型"调用函数"来填表 ​

Function Calling（也叫工具调用）是结构化输出的"进阶版"。它的思路很巧妙：你不是直接让模型输出 JSON，而是给它定义一个"函数"，让它决定要不要调用这个函数、传什么参数。

打个比方。你去医院看病，医生不会把诊断结果写成一封信给你，而是填一张处方单。处方单有固定格式：药品名、剂量、用法、天数。Function Calling 就是给模型发了一张"处方单模板"，模型诊断完了，按模板填参数。

具体怎么做？你在请求里定义一个 tools 数组，每个工具就是一个函数签名：叫什么名字、需要什么参数、每个参数什么类型、是否必填。模型看完后，如果觉得自己该调用某个工具，就会输出一个标准的工具调用结构——里面包含函数名和参数对象。

这个参数对象，天然就是结构化的 JSON。你前端拿到后直接提取字段，连解析都省了。

Function Calling 比 JSON Mode 强在哪？

第一，自带类型系统。 你定义参数的时候就说清楚了 "amount 是 number"、"tags 是 string 数组"，模型不容易填错类型。

第二，支持多工具。 你可以给模型定义十几个工具（查天气、算汇率、发邮件……），模型根据用户的问题自己判断该调用哪个。这相当于让模型自己选"填哪张表"。

第三，可扩展性强。 工具可以是真的去调外部 API，也可以是纯"格式化输出"的虚拟工具。后者就是我们说的"结构化输出"场景。

前端同学可以把 Function Calling 理解为：你定义了一个 TypeScript 接口，模型帮你生成符合这个接口的对象。接口即契约，契约即格式。

方法三：约束解码 —— 从根上"锁死"格式 ​

JSON Mode 和 Function Calling 都属于"软约束"——你告诉模型"请输出 JSON"，它理论上应该听，但万一模型"犯浑"呢？毕竟大模型本质上是概率生成，它有权选择下一个 Token。

约束解码（Constrained Decoding） 是"硬约束"：在模型生成每一个字的瞬间，就通过算法限制它"只能选合法的 Token"，从根上杜绝格式错误。

打个比方。JSON Mode 就像你跟小孩说"请把积木搭成房子形状"——他听懂了，但手一抖可能搭歪。约束解码就像你给了他一个房子形状的模具——积木只能往模具的格子里放，想搭歪都不可能。

技术原理上，约束解码会在每一步生成时，用一个"合法性检查器"判断：当前已生成的部分 + 下一个候选 Token，是否还满足你规定的格式（比如 JSON Schema）。如果不满足，这个候选 Token 的概率直接被打成零，模型根本选不到它。

常见的约束解码实现有：

  • Outlines：用正则表达式或 JSON Schema 定义格式，生成过程实时约束。
  • Guidance：微软出的库，支持更复杂的模板约束（比如"先输出 A，再输出 B，B 必须是数字"）。
  • vLLM 的 Guided Decoding：在推理框架层面集成约束解码，性能最好。

约束解码的代价是什么？计算开销略高（每一步都要检查合法性），而且如果约束写得太死、太复杂，模型可能"卡死"——每一步可选的 Token 太少，最后生成的东西语义不通。

所以工程上的建议是：约束给"型"，不要给"意"。也就是说，约束 JSON 的字段名和类型，但不要约束每个字段的具体内容。内容的准确性靠 Prompt 质量和模型能力来保证，格式的正确性靠约束解码来保证。各司其职。

三种方法怎么选？一张表说清楚 ​

场景推荐方案原因
只需要 JSON，字段简单JSON Mode接入成本最低，一行参数搞定
需要强类型、多字段、复杂嵌套Function Calling自带 Schema 定义，类型安全
对格式正确性要求极高（如金融、医疗）约束解码从生成层面杜绝格式错误
字段不确定、需要模型动态决定Function Calling + 多工具模型自己选工具，自己填参数

你可以把这个选择过程想象成安全等级递进：JSON Mode 是"请自觉排队"，Function Calling 是"有保安维持秩序"，约束解码是"装了安检门，带错东西根本进不来"。

前端工程里的几个实用技巧 ​

1. Prompt 里一定要给示例

即使开了 JSON Mode，也最好在 Prompt 里放一个完整的输出示例。模型是"模仿动物"，你给例子，它模仿得最准。

请按以下 JSON 格式输出，不要添加任何解释：

2. 处理模型"加戏"

有些模型即使开了 JSON Mode，也会先输出一句 "以下是您要求的 JSON 数据：" 再跟 JSON。前端解析前先 trim，再用正则提取第一个 {...} 或 [...] 块，别指望模型 100% 听话。

3. 用 Zod 做运行时校验

模型输出的 JSON 结构对了，但字段值可能不对（比如把金额填成了字符串 "1280" 而不是数字 1280）。前端拿到后用 Zod 跑一遍 Schema 校验，早发现早处理。

4. 温度设低一点

生成结构化输出时，建议把 temperature 调到 0.1~0.3。温度越高模型越"有创意"，越容易在格式上搞事情。结构化任务不需要创意，需要稳定。

小结 ​

结构化输出是 AI 应用从" demo "走向"产品"的关键一步。用户看不到模型内部怎么想的，但他们能看到你前端展示的数据对不对、整不整齐。

记住三个层次：

  1. JSON Mode：告诉模型"请写 JSON"——软约束，最简单。
  2. Function Calling：给模型一张"处方单模板"——带类型、可扩展、最常用。
  3. 约束解码：装上"模具"，从生成根上锁死格式——最严格，适合高要求场景。
