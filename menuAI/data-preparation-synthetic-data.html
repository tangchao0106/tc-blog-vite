数据准备与合成数据：喂给模型什么「食」 ​

一个容易被忽略的事实 ​

聊微调的时候，大家的目光总是集中在算法上：LoRA 还是全量？学习率多大？训练几个 epoch？

但做过的都知道，真正决定微调效果的，80% 是数据，20% 才是算法。

打个比方：你要培养一个实习生。你的教学水平（算法）当然重要，但如果你给他的学习材料（数据）全是过时的、矛盾的、或者根本跟他的工作不相关——再怎么教也白搭。

这一篇，我们就把焦点放在数据上。高质量的微调数据从哪来？怎么整理？不够怎么办？

什么样的数据是好数据？ ​

先给"好数据"画个像：

多样性要够。 如果你想让模型学会写 SQL，光给它"SELECT * FROM users"是不够的。它需要看到各种花样：多表 JOIN、子查询、窗口函数、不同数据库的方言、出错的 SQL 和对应的修正……记住一条经验法则：微调不是教模型"记住答案"，而是教它"掌握模式"。模式只能从多样性中来。

质量要一致。 一条完美的指令 + 一条垃圾输出 = 整体质量被拉低。数据不是越多越好，100 条精心打磨的数据可能胜过 10000 条粗糙数据。想象你在教一个人做菜——给他看十道米其林级别的菜谱，比给他看一百道"少许盐、适量油"的模糊菜谱有用得多。

格式要统一。 如果你用 JSON 格式标注对话，就全部用 JSON；如果你用 Markdown 分隔角色，就全部用 Markdown。格式不一致会让模型产生混淆——它不知道到底是该输出 JSON 还是 Markdown，最后可能输出一个诡异的混合体。

覆盖要均衡。 你不能只有"难"的数据，也不能只有"简单"的数据。理想的数据分布应该像一个金字塔：大量中等难度的样本打底，配一些简单和困难的样本做边界。这跟人类学习一样——一直在舒适区学不到东西，一直在恐慌区会崩溃。

数据的"三件套"：指令、输入、输出 ​

现在主流的数据格式是 Instruction-Following 格式，结构很清晰：

  • 指令（Instruction）：告诉模型要做什么。比如"把下面这段话翻译成英文"。
  • 输入（Input）：给模型的具体素材。比如待翻译的中文段落。
  • 输出（Output）：你期望模型给出的答案。比如翻译好的英文段落。

有些任务不需要输入（比如开放式问答），那就是只有 Instruction + Output。

看上去简单？真正的坑在细节里。

指令要具体，但不要啰嗦。 "翻译成英文"太模糊——是美式英语还是英式英语？正式还是口语？好的指令应该是"将以下中文翻译为美式商务英语，保持原文的正式语体"。

输出要高质量，而且要"想得通"。 如果你的数据里输出质量参差不齐，模型会学到"有时候可以随便回答"。另外，如果是一个推理任务，输出里最好包含推理过程（Chain-of-Thought），这样模型学到的不只是结论，还有推理方法。

正负样本的比例要合理。 有些场景你需要告诉模型"什么时候该拒绝"。比如做一个客服机器人，你应该加入一些用户问无关问题、模型礼貌拒绝的例子。没有负样本，模型会对什么请求都试图回答。

数据从哪来？五大来源 ​

来源一：现成数据集。 开源社区已经积累了大量高质量数据集。Alpaca、ShareGPT、OpenOrca、UltraChat……这些都是经过验证的数据集。直接用、或作为种子数据再加工，是最省力的起点。

来源二：人工标注。 质量最高、成本也最高。适合核心技术场景或商业产品。找领域专家标注，一条数据可能要几十块到上百块。10000 条高质量标注数据可能要花几十万——这还只是数据成本，不算训练成本。

来源三：从用户交互中挖掘。 如果你已经有一个产品在跑，用户的真实对话就是金矿。需要注意的是用户数据涉及隐私，脱敏和合规是前提。另外用户对话往往质量参差——他们问得清楚的要保留，问得模糊的要么修正、要么丢弃。

来源四：爬取 + 清洗。 从论坛（Stack Overflow、知乎）、文档（官方 API 文档、技术手册）、问答平台收集数据。关键不是爬取，而是清洗——去重、去广告、去无意义内容、格式标准化。

来源五：合成数据。 这是近几年最火的数据获取方式，我们展开讲。

合成数据：用 AI 造数据喂 AI ​

合成数据的思路很直接：让一个强模型（如 GPT-4、Claude）帮你生成微调数据，然后用这些数据去训练你的目标模型。

你可能会疑惑：这不就成了"用 GPT-4 的数据训练自己的模型，那直接用 GPT-4 不就好了"？

答案是：场景不同。GPT-4 是通用模型，又贵又慢，而且你无法控制它的私有部署。你自己的模型可以针对特定场景深度优化、可以离线部署、可以控制成本。

合成数据有几个经典套路：

套路一：Self-Instruct（自我指令）。 给 GPT-4 几个示例，让它模仿着生成更多类似的任务指令。有人说"这不就是套娃吗"，对，本质上就是套娃——但效果出奇地好。你给它 10 个种子指令，它能生成 1000 个变体。

套路二：Evol-Instruct（指令进化）。 不是从零生成，而是在已有指令的基础上做"难度升级"。比如把一个简单的翻译任务重写为"翻译并保持原文的修辞手法"；把一个数学题重写为需要多步推理的复杂版本。这样你能得到一个从简单到困难的完整数据链条。

套路三：反向生成。 先写好期望的输出，让强模型反推出对应的指令。这特别适合那些"你知道理想答案长什么样，但不知道怎么描述任务"的场景。

套路四：多轮对话构建。 模拟真实的用户-AI 交互流程。你给强模型一个角色设定（比如"你是一个前端技术顾问"），让它自己生成用户问题和回答。注意要加入纠错、追问、澄清这些真实对话中的常见情况。

合成数据不是银弹 ​

合成数据虽然好用，但有几个坑必须跳过去：

模型偏差会遗传。 你用的是 GPT-4 生成的数学题，GPT-4 自己可能在某些数学类型上有系统性盲区——这些盲区会完整地遗传给你的目标模型。所以不要只用一个大模型生成所有数据，混用多个强模型可以有效减轻偏差。

多样性幻觉。 强模型生成 10000 条数据，表面上每一条都不一样，但仔细看可能都是同一套思维模式的不同变体。解决方案是：在 Prompt 里显式要求多样性（"请生成涵盖不同领域、不同难度、不同对话风格的任务"），并且在生成后做语义聚类检查。

幻觉污染。 如果强模型在生成数据时自己产生了幻觉（比如捏造了不存在的 API），这些幻觉会被当成正确答案教给你的目标模型。关键领域的合成数据必须经过人工抽检。

隐私边界。 如果你的业务涉及敏感数据，不要把它们喂给 GPT-4 来生成合成数据——除非你用的是 API 的商业版（有数据不用于训练条款）。一个安全的做法是用本地部署的强模型做数据生成。

实操流程：一次完整的数据准备 ​

想象你要微调一个前端代码审查助手。完整的数据准备流程大概是这样的：

Step 1：定义数据画像。 列出你要覆盖的场景矩阵：代码风格检查、安全漏洞检测、性能优化建议、可访问性审查……每个场景大概需要多少条数据，难度分布如何。

Step 2：收集种子数据（50-100 条）。 自己手写或者找团队里资深的前端写好 50-100 条高质量示例。这是整个数据池的"锚点"。

Step 3：生成合成数据（目标 5000 条）。 把种子数据喂给 GPT-4，用 Evol-Instruct 不断扩展和变体。每条生成的数据附带一个"来源标注"——是种子数据、是变体、还是全新生成。

Step 4：自动清洗。 用脚本做：去重（语义去重而非字符去重）、格式校验、长度过滤（太短和太长的都剔除）、语言检测（别混入其他语言）。

Step 5：人工抽检（抽 5-10%）。 随机抽 250-500 条，逐条检查质量。如果合格率不到 90%，退回 Step 3 调整 Prompt 重新生成。

Step 6：数据分割。 按 8:1:1 或 9:1 分成训练集、验证集、测试集。验证集和测试集绝对不能包含合成数据——必须全部是人工标注的，这样才能客观衡量模型效果。

一点心态上的建议 ​

做数据准备这件事，最容易犯的错误是"贪多"。总觉得数据越多越好，于是花了大量时间跑脚本生成几万条数据，结果质量稀烂，训练出来效果还不如用 500 条精细数据。

记住一个不等式：10 条人的数据 > 100 条优质 AI 生成数据 > 10000 条低质数据。

另外，数据准备不是一次性的事。第一版训练完你会发现问题——某个场景总是翻车，那就在那个场景上多补几十条数据。"训练→发现问题→补数据→再训练"，这才是一个健康的迭代循环。
